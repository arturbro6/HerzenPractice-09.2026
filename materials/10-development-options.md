## Возможные направления

### Сохранение данных

Добавить запись задач в JSON-файл и загрузку при запуске. Это позволит сохранять состояние между сеансами без преждевременного подключения базы данных.

### Обработка ошибок

Выделить явные результаты операций для неверного ввода, пустого названия и отсутствующего ID. Затем отразить эти случаи в тестах.

### Расширение тестов

Добавить граничные и табличные сценарии, сохраняя в каждом тесте понятное разделение исходных данных, вызова и ожидания.

### HTTP API

После стабилизации логики заменить консольный способ взаимодействия HTTP-обработчиками. Операции создания, чтения, изменения и удаления задач могут стать основой REST API.

### База данных

Подключать базу данных целесообразно после появления HTTP API и требований к долговременному хранению. На первом этапе достаточно одной таблицы задач и понятных операций чтения и записи.

### Связь с проектом repair-service

Следующий учебный проект `repair-service` развивает те же идеи на предметной области заявок на ремонт: идентификаторы, статусы, поиск, изменение данных, тестирование и последующий переход к HTTP и SQL. На дату завершения практики этот проект находится в разработке, поэтому в отчёт включён только анализ направления.

## Предлагаемая последовательность

1. Улучшить обработку ошибок и тестовые сценарии.
2. Добавить файловое хранение.
3. Освоить HTTP на тех же операциях.
4. Подключить SQL и перенести хранение в базу данных.
5. Развивать `repair-service` без усложнения архитектуры заранее.
